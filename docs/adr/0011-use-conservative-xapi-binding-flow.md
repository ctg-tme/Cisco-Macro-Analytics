# Use conservative origin-based xAPI Binding Flow

ADR 0013 supersedes this decision's treatment of Unresolved Identifier Findings and overlap priority. ADR 0014 renames the user-facing xAPI Flow Frontier to Dynamic xAPI Reference and changes its Review Priority to Advisory. One consolidated Dynamic xAPI Reference per macro retains every opaque boundary and references only the observations that establish that boundary.

Binding propagation respects assignment order and statically resolvable control flow. A use reached by both proven xAPI and non-xAPI or unknown values is Partial and is not reconstructed as a Canonical xAPI Reference, while independently proven routes and source occurrences before a later reassignment remain valid evidence.

The analyzer will use Seeded xAPI Data Flow: it starts only from statically proven `"xapi"` module import, require, or re-export origins and never seeds analysis from property names or call shapes that merely resemble xAPI. It will follow explicitly proven propagation through aliases, destructuring, call-site-specific argument-to-parameter mappings, returns, instance properties, exports, imports, and equivalent abstractions, including across supplied dependency files when the applicable imports and calls resolve statically. A callable is not globally marked as xAPI: separate xAPI Call Contexts allow one call receiving a proven xAPI Binding to attribute downstream touchpoints while another call receiving a mock or unrelated object makes no xAPI claim. Each proven flow records an ordered xAPI Binding Route whose hops identify the exact local binding name, transformation, and Source Reference without claiming runtime execution. When a seeded route enters an unavailable or dynamic transformation, its last proven hop becomes a Dynamic xAPI Reference: the affected observation family becomes Partial, a consolidated Advisory identifies the opaque boundary, and values beyond it are not assumed to remain xAPI. All independently proven routes remain analyzed. When the route and every API segment resolve, the analyzer reconstructs a Canonical xAPI Reference—kind, normalized path, operation, preferred New-style display expression, and official RoomOS documentation locator—independently of the submitted binding names and syntax style; the observation retains the source's actual syntax classification. Repeated-reference and cross-macro-overlap rules compare this canonical kind, path, and operation, so direct and abstracted touchpoints converge regardless of binding route, root name, submitted syntax, or arguments. Dynamic segments retain only their known prefix and limitation; no complete path or documentation locator is guessed. A proven module-root binding whose local name is not exactly `xapi` contributes to one consolidated Nonstandard xAPI Root Binding Warning per macro without reducing coverage. Regardless of that root's local name, each proven downstream abstraction route that reaches an xAPI Touchpoint contributes to one separate Informational xAPI Abstraction Finding per macro; a proven flow without a detected touchpoint remains neutral ledger evidence. The root-name Warning and abstraction Informational Finding may therefore coexist and reference the same route for different reasons. This deeper static data-flow model costs substantially more parser and analysis complexity than syntax matching, but it recognizes ordinary abstraction without converting naming conventions or possible runtime values into false xAPI evidence.
